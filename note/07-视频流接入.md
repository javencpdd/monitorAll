# 07 视频流接入（pull / publish / 播放链路）

> 视频是本系统唯一**不走 Go 后端数据面**的通道：像素流从浏览器直连 MediaMTX，
> Go 只负责「注册路径 + 下发播放地址」。这条链路上的坑集中在 **模式判定** 与 **地址生成** 两处。

## 7.1 先分清三种角色

| 概念 | 含义 | 后端 `source` 字段 |
|---|---|---|
| **pull**（拉流） | 填远端 `rtmp://` / `rtsp://` 地址，MediaMTX 主动去拉 | 完整原始 URL（**含用户名密码**） |
| **publish**（收流） | 不填地址，只给 MediaMTX 路径，等远端推流 | `publisher` |
| **external** 模式 | MediaMTX 是外部已部署的，后端不注册路径 | ——（`mode: external` 时跳过 `PathAdd`） |

判定在 `server/internal/adapter/video/video.go`：
`normalizeMode()` 缺省 **pull**；`sourceFor()` 里 `mode == publish` **或** `isLocalPublishLocked()` 为真 → `publisher`。

> ⚠️ `isLocalPublishLocked()` 只认 **rtmp/rtmps**（RTSP 一律 false），且要求
> 「端口 == `mediamtx.portRtmp`」**且**「主机是 127.0.0.1 / localhost / `server.lanHost`」。
> 换句话说：**把 RTMP 地址填成指向本机 MediaMTX，即便没选 publish，也会被识别成 publisher。**

配置段（`server/config.yaml`）：

```yaml
mediamtx:
  mode: embedded        # embedded | external
  apiBase: "http://127.0.0.1:9997"
  publicHost: ""        # 留空 = 用 server.lanHost
  publicScheme: "http"
  portRtmp: 1935        # 裸跑；Docker Compose 方案是 1936
  portHls: 8888
  portWebrtc: 8889
  flvBase: ""           # 外部 HTTP-FLV 网关根地址
```

## 7.2 ⭐ `sourceOnDemand` 与 publisher 互斥 → 400

**现象**：publish 模式创建数据源时，MediaMTX 返回 400，路径注册失败（后端只 warn 不致命，容易忽略）。

**根因**：`PathAdd` 原先固定发 `sourceOnDemand: true`。MediaMTX 对被动等待推流的源直接拒绝：

```
"'sourceOnDemand' is useless when source is 'publisher'"
```

`sourceOnDemand` 只对「主动去拉」的源有意义——publisher 本来就是有人推才存在，按需拉无从谈起。

**修复**（`server/internal/media/mediamtx.go:146`）：

```go
payload := map[string]any{"source": source, "sourceOnDemand": source != SourcePublisher}
```

**教训**：MediaMTX 的配置字段**按源类型有条件生效**，写通用封装时必须先搞清楚每种 source 的语义。
另外注意——路径注册失败后端只记 `Warn` 就继续（`video.go:146`），**不会中断数据源**：
路径可能已存在，或 API 只读。所以"注册失败"的日志未必是真错误，要结合 MediaMTX 自身状态看。

## 7.3 RTSP 摄像头（四条容易漏的细节）

1. **协议白名单**：`ParseStreamURL` 只放行 `rtmp / rtmps / rtsp / rtsps`，其余返回 `InvalidURL`。
2. **默认端口**：RTSP 缺省 **554**（RTMP 是 1935），`defaultPortFor()` 按协议取值。
3. **凭据必须保留**：RTSP 摄像头普遍带账号，所以 `StreamInfo.Raw` **原样保存含 `user:pass@` 的完整串**，
   `sourceFor()` 传给 MediaMTX 的也是 Raw。前端别"好心"把密码剔掉——剔了就 401。
4. **传输方式默认 TCP**：UDP 下 RTSP 极易花屏/连不上，所以 `rtspTransportOf()` 对非法值**回落 tcp**（不是 udp）。
   可调 `tcp / udp / automatic`，实际写入 `rtspTransport` 字段（`server/internal/media/mediamtx.go:43`）。

**路径可多段**：`rtsp://user:pass@host:554/Streaming/Channels/101` 这种海康格式是合法的，
解析器刻意允许多段 path，别"修正"成只取最后一段。

## 7.4 ⭐ 播放地址永远要用 publicHost（127.0.0.1 陷阱）

`BuildPlayURLs()` / `BuildPublishURLs()`（`server/internal/media/url.go`）生成的是**给浏览器用**的地址，
所以 host 取的是「浏览器能连到的那张网卡」，而不是 API 侧的地址：

```
publicHost → cfg.Server.LANHost → 127.0.0.1（兜底）
```

**典型事故**：不配 `mediamtx.publicHost` 也不配 `server.lanHost` →
地址落成 `http://127.0.0.1:8889/...`，**只有坐在服务器前的那台机器看得到画面**，
局域网其它机器黑屏但不报错。详见 [02 §2.6](./02-后端与协议.md)。

publish 模式创建的通道，meta 里会回传 `publishUrl`(WHIP) / `publishRtmpUrl`(RTMP)，
前端向导会显示 + 提供复制按钮。**这两个地址同样走 publicHost**，
没配好就会出现「推流地址是 127.0.0.1，机器人推不过来」。

## 7.5 播放链路三选一：默认降级目标是 **HLS**，不是 FLV

> 这是**开发中途改过设计**的一处，务必留意：**PRD/架构早期写的「HTTP-FLV 兜底」被推翻了。**

**原因**：MediaMTX 原生**不支持** HTTP-FLV（官方 issue #1460 明确拒绝实现）。
所以 FLV 只有在后端配置了 `mediamtx.flvBase`（外部 FLV 网关，如 SRS / ZLMediaKit / nginx-http-flv）时才会出现。

实际优先级（`web/src/utils/video.ts` → `fallbackOrder()`）：

```
首选协议（默认 webrtc） → webrtc → hls → flv
```

且只保留「后端真的下发了 URL」的协议（`availableProtocols()` 过滤空串）。

| 协议 | 传输 | 延迟 | 备注 |
|---|---|---|---|
| **WebRTC (WHEP)** | 原生 `RTCPeerConnection`，无第三方库 | 亚秒级 | 需要安全上下文（见 7.6） |
| **HLS** | hls.js，`lowLatencyMode` + `liveSyncDuration=3s` | 1–3s | **默认兜底**；Safari 走原生 HLS（`el.src` 直喂） |
| **FLV** | mpegts.js | 1–3s | 依赖 `flvBase`，未配则不存在这项 |

```ts
// web/src/utils/constants.ts
export const VIDEO_MAX_MSE_BUFFER_SEC = 3   // 直播缓冲目标，别调大
```

> ⚠️ **前后端降级顺序不一致（已知，暂不影响使用，改代码时注意）**
> 前端 `web/src/utils/video.ts` 的 `fallbackOrder()` 是 `webrtc → hls → flv`；
> 后端 `server/internal/media/url.go` 的 `PickProtocol()` 是 `webrtc → flv → hls`。
> 由于实际播放由前端决定协议，后端这个顺序只在"后端替你挑首选"时生效，
> 但两者语义不一致容易造成困惑（配了 flvBase 时后端会挑 flv、前端自选时优先 hls）。
> 若哪天要让它俩统一，改的是前端还是后端要想清楚再动。

## 7.6 WebRTC 的两个技术细节

**(a) 必须等 ICE 收集完成再发 offer。**
早期实现 `createOffer()` 后直接 POST，SDP 里没有 candidate → 协商失败。
现在 `waitIceGatheringComplete()` 最多等 2s 再发（`video.ts:87`），超时也继续，不阻塞。

**(b) WebRTC 是安全上下文特性。**
跨主机通过 `http://` 访问看板时 `window.isSecureContext === false` → WHEP 直接不可用。
前端用 `isPlayableSecureContext()` 判定并把 webrtc 从候选里剔除。
详见 [02 §2.7](./02-后端与协议.md)。

**(c) 多 track 会抖动。** MediaMTX 的网络抖动可能让 `ontrack` 多次触发；
实现里用**一条稳定的 MediaStream 汇聚**所有 track，避免 `srcObject` 反复赋值。

---

## 7.7 降级不是一次性的：会定期探测回切

降级到 HLS 后，`probeWebrtc()` 每隔 `VIDEO_RETRY_PREFERRED_DEFAULT_SEC = 30` 秒
**后台探测一次 WHEP 是否恢复**（只协商、不 attach 到 video 元素、不产生画面），
成功后自动切回首选协议。所以看到日志里反复出现协商请求，是**预期行为**，不是 bug。

## 7.8 症状速查

| 现象 | 优先怀疑 |
|---|---|
| 本机正常、其它机器黑屏 | `mediamtx.publicHost` / `server.lanHost` 没配 → 地址是 127.0.0.1（7.4） |
| publish 模式注册路径报 400 | `sourceOnDemand` 与 publisher 互斥（7.2） |
| RTSP 摄像头连不上 / 花屏 | 传输方式被 UDP 拖累 → 用 `tcp`；检查凭据是否被剔除（7.3） |
| 完全没有 FLV 选项 | `flvBase` 为空（正常，默认走 HLS）（7.5） |
| 延迟很大（>5s） | 落在 HLS 且 `VIDEO_MAX_MSE_BUFFER_SEC` 被调大；或 WebRTC 因非安全上下文被跳过（7.5 / 7.6） |
| 画面卡住后自动变模糊/重连 | 降级编排在工作，看是不是 30s 周期探测（7.7） |
| 填了 RTMP 地址却变成"等推流" | `isLocalPublishLocked()` 判定成本机推流（7.1）——改远端 IP 或显式选 pull |

---

## 7.9 一条设计红线

**像素流绝不经过 Go 后端。** 后端扮演的是"配置员"角色：注册路径、算地址、下发。
一旦有人图省事让 Go 转发视频流，延迟和内存都会失控。这条在 ARCH §11 有明确约定，别破。
