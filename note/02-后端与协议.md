# 02 后端与协议（MediaMTX / WebSocket / 播放地址）

## 2.1 MediaMTX 配置字段分两派类型（导致容器反复重启）

**现象**：`bluenviron/mediamtx:latest` 容器 crash-loop，9997/8888/8889 不可用。

**根因**：两类字段类型不同，抄官方示例容易串：

| 字段 | 类型 | 正确写法 |
|---|---|---|
| `api`、`rtmp`、`hls`、`webrtc`、`metrics`、`pprof` | **布尔** | `api: true` |
| `rtmpEncryption`、`webrtcEncryption`、`hlsEncryption`、`apiEncryption` | **字符串 alias** | `"no"` / `"yes"` / `"strict"` |

- 写 `api: yes` → `cannot unmarshal string into Go value of type bool`
- 写 `rtmpEncryption: false` → `cannot unmarshal bool into Go value of type conf.alias`

**教训**：MediaMTX 的字段类型必须逐个查证，**最小配置**出错面最小：

```yaml
rtmpAddress: :1936
api: true
paths:
  all_others: {}
```

（其余用官方默认：8888/8889/9997、不加密、`AllowOrigin: ['*']`、`hlsVariant: lowLatency`。）

## 2.2 MediaMTX API 401：默认 IP 白名单（Docker 必踩）

**现象**：容器 Up、日志零错误、端口全监听，但 `curl 127.0.0.1:9997/v3/paths/list` 返回
`HTTP 401 {"error":"authentication error"}`，后端永远注册不了路径 → 视频不出画面。**裸跑正常、Docker 异常**。

**根因**：MediaMTX v1.21.1 有**代码内置默认**认证策略——`api`/`metrics`/`pprof` 只允许
`ips: ["127.0.0.1","::1"]`，**yml 里不写 `authInternalUsers` 也照样生效**。
Docker 中后端容器经 docker-proxy 访问 `mediamtx:9997`，源 IP 是网桥 `172.x`（非 127.0.0.1）→ 一律 401。

**对照实验**（用环境变量把端口挪开跑临时实例）：

| 配置 | `curl 127.0.0.1` | `curl <宿主机IP>`（模拟 172.x 源） |
|---|---|---|
| 省略 `authInternalUsers` | 200 | **401** |
| api 权限 `ips: []` | 200 | **200** |

**修复**：显式写 `authMethod: internal` + 用户条目，**`ips: []` 表示不限 IP**（关键：不能抄官方默认 yml 的 `["127.0.0.1","::1"]`）：

```yaml
authMethod: internal
authInternalUsers:
  - user: any
    pass:
    permissions:
      - action: publish
      - action: read
      - action: playback
    ips: []
  - user: any
    pass:
    permissions:
      - action: api
      - action: metrics
      - action: pprof
    ips: []          # ← 关键
```

**排查技巧**：
- 用 `MTX_APIADDRESS=:19997 MTX_HLSADDRESS=:18888 ...` 覆盖端口，可在**不影响运行中容器**的前提下起临时实例验证；
- `docker run --rm --entrypoint cat bluenviron/mediamtx:latest /mediamtx.yml` 才是导出官方默认配置的正确写法（直接 `cat` 会被当成二进制参数报 `unexpected argument`）。

## 2.3 改了 MediaMTX 配置却不生效：bind mount 绑定的是 inode

**现象**：宿主机改了 `mediamtx.yml`，容器内仍读旧内容。

**根因**：Docker 单文件 bind mount 绑定 **inode**；编辑器原子替换（临时文件 + rename）保存后，容器内仍指向旧 inode。MediaMTX 也不自动重载。

**修复**：每次改完 `docker compose restart mediamtx`。

## 2.4 配置文件查找顺序 & 空配置启动

MediaMTX v1.21.1 按 `<cwd>/rtsp-simple-server.yml` → `<cwd>/mediamtx.yml` → `/usr/local/etc/mediamtx.yml` → `/usr/etc/mediamtx.yml` → `/etc/mediamtx/mediamtx.yml` 查找。

都找不到则 **WARN `using an empty configuration`** 并以默认配置启动（api 可能被关闭 → 后端连不上 :9997）。

**修复**：要么 `cd` 到配置目录，要么**显式传路径**：

```bash
~/monitorAll/mediamtx/mediamtx ~/monitorAll/mediamtx/mediamtx.yml &
```

## 2.5 `PathAdd` 的两个坑

| 问题 | 现象 | 修复 |
|---|---|---|
| `sourceOnDemand: true` 用在 publisher 源 | MediaMTX 返回 `400 'sourceOnDemand' is useless when source is 'publisher'` | `sourceOnDemand: source != SourcePublisher`（实测 false/省略=200，true=400） |
| 重复注册 | 重连/重启时刷 WARN `[50003] path already exists` | 对 `400 + "already exists"` 视为成功 |

## 2.6 播放地址永远返回 127.0.0.1（只有本机看得到画面）

**现象**：本机播正常，其它主机 `m3u8` 500 / `whep` 400。

**根因**：`BuildPlayURLs` 回退链是 `publicHost → cfg.Server.LANHost → "127.0.0.1"`。
后端运行时虽然用 `CollectLANHosts()` 探测到了 LAN IP，**却从不回填进 cfg** → 永远退化成 127.0.0.1。

**修复**（`cmd/monitorall/main.go`，紧跟 `lanHosts := CollectLANHosts()`）：
`cfg.Server.LANHost` 为空时回填 `lanHosts[0]`；`cfg.MediaMTX.PublicHost` 为空时取 LANHost。

**注意**：自动取的是 `lanHosts[0]`；若其它主机经另一个 IP 访问，需在配置里显式设 `mediamtx.publicHost`。

**验证（无需浏览器）**：起临时实例 + Node WS 探帧看 `payload.urls`：

```bash
MONITORALL_SERVER_HTTPADDR=:9080 MONITORALL_STORE_DSN=/tmp/vtest/monitorall.db \
MONITORALL_SERVER_DATADIR=/tmp/vtest ./server/bin/monitorall --config server/config.yaml
```

## 2.7 WebRTC 是安全上下文特性（跨主机 HTTP 下不可用）

**现象**：其它主机用 `http://10.42.0.1:8080` 打开时 WHEP 400；本机 localhost 正常。

**根因**：`window.isSecureContext` 在非 HTTPS（且非 localhost）下为 false，WebRTC 不可用。

**修复**：跨主机场景卡片「首选协议」选 **HLS**（`utils/video.ts` 已有 `isSecureContext` 判断）。纯 HTTP 下不要选 WebRTC。

## 2.8 WS 心跳与读超时：超时必须大于心跳周期（曾导致每 12 秒断连）

**现象**：日志里每条 WS 连接**精确存活 12.0 秒**后关闭重建，3 个标签页全部如此，无限重连；且**没有**"连续丢失 pong"告警。

**根因**：`ws/conn.go` 的 `case OpHello:` 里，握手后读超时写成
`PongTimeoutMs(3000) × (MaxMissedPong+1=4) = 12s`，而服务端心跳周期 `pingIntervalMs=15000`。
心跳是**服务端**主动发，客户端收到 ping 才回 pong——第一个 ping 要 15s 才到，读超时 12s 已经先触发。
即：把"等待单个 pong 的超时"误用成了"整条连接的读超时"。

**修复（两处缺一不可）**：
1. 新增 `aliveDeadline()`：读超时 = 心跳周期 × (MaxMissedPong+1) = 15s×4 = 60s；
2. readPump 里**每读到一条上行消息就顺延读超时**，否则只是把 12s 循环变成 60s 循环。

**教训**：凡是"读超时/空闲超时"与"心跳周期"并存，必须保证 **超时 > 心跳周期**，且超时随每条上行消息顺延。

**验证**：`scripts/ws-keepalive-probe.mjs`（Node 全局 WebSocket，注意用 `addEventListener` 而非 `.on()`）。实测 40s / 70s 均存活 ✅。

## 2.9 WS 握手竞态：`BAD_REQUEST：请先发送 hello`

**现象**：控制台 `[ws] BAD_REQUEST：请先发送 hello`；看板卡片永远没数据，但向导预览有画面。

**根因**：`ws/client.ts` 的 `onopen` 里 **hello 用 `setTimeout(0)` 异步发送，而订阅重放是同步发送** →
subscribe 抢在 hello 前到达被拒 → 订阅静默丢失且不重试（重连重放还是同样竞态）。

**修复**：
1. hello 改为 `onopen` 内**同步**发送；
2. `send()` 在未收到 welcome 前把除 hello 外的消息排入 `pending`，welcome 到达后按序补发；
3. onclose 清空状态。

## 2.10 WS 协议速查（手写探针用）

```
客户端 → hello  { op:'hello', protocol:1, clientId }
服务端 → welcome{ connId, protocol, serverTimeMs, heartbeatIntervalMs, pingIntervalMs }
客户端 → subscribe  { op:'subscribe',   channelIds:[...], ref }
客户端 → unsubscribe{ op:'unsubscribe', channelIds:[...], ref }
服务端 → subscribed { ref, results:[{channelId, ok, status}] }
服务端 → frames     { ... }       按通道下发归一化帧
服务端 → ping       客户端必须回 pong
```

**诊断要点**：后端 WS 日志里的 **`channels` 计数**极有价值——
`channels > 0` 说明卡片已挂载并订阅；`channels = 0` 说明画布根本没渲染（见 [03](./03-前端框架与布局.md)）。
