# 06 调试方法论（本环境没有浏览器，如何取证）

> **前提**：本环境**无法做任何浏览器自动化**（Chrome 因 `ptrace` 崩溃；`agent-browser` 的 `open` 超时后守护进程卡死）。
> 前端也无 vitest/jsdom。所以一切结论必须靠"旁证"。

## 6.1 四板斧

| 手段 | 用途 | 示例 |
|---|---|---|
| ① **后端日志** | 判断连接/订阅/适配器的真实行为 | `logs/monitorall.log`、`logs/mediamtx.log` |
| ② **REST 直查** | 隔离前后端：接口正常说明问题在前端 | `curl --noproxy '*' ... /api/v1/dashboards/{id}` |
| ③ **Node WS 探针** | 绕过浏览器直接验证帧下发 | `scripts/ws-keepalive-probe.mjs` |
| ④ **构建产物 grep** | 证明改动**真的进了产物** | `grep -o '\.ma-drawer__body\[[^]]*\]{[^}]*}' dist/assets/*.css` |

**第 ④ 项尤其重要**：改了代码但用户没重启 / 没强刷，是本项目"修复无效"的最常见原因。
每次交付前都用它自证一次。

## 6.2 WS 探针（无浏览器验证后端帧下发）

协议速查见 [02 §2.10](./02-后端与协议.md)。Node 22 有全局 `WebSocket`，注意用 **`addEventListener`** 而非 `.on()`：

```js
const ws = new WebSocket('ws://127.0.0.1:8080/api/v1/ws')
ws.addEventListener('open', () => ws.send(JSON.stringify({ op: 'hello', protocol: 1, clientId: 'probe' })))
ws.addEventListener('message', (e) => {
  const m = JSON.parse(e.data)
  if (m.op === 'welcome')  ws.send(JSON.stringify({ op: 'subscribe', channelIds: [CHANNEL_ID], ref: 'r1' }))
  if (m.op === 'ping')     ws.send(JSON.stringify({ op: 'pong' }))
  if (m.op === 'frames')   console.log('收到帧', m)
})
```

**实测用途**：验证心跳修复（观察 40s / 70s 存活）、验证播放地址（看 `payload.urls` 是否含 LAN IP）、
验证通道是否有数据。

## 6.3 日志量化（把"感觉"变成数字）

**案例：定位 WS 每 12 秒断连。** 按 `connId` 配对「建立」与「关闭」消息，计算存活时长分布：

```python
open_t, pairs = {}, []
for line in open('logs/monitorall.log', encoding='utf-8', errors='replace'):
    if '"module":"ws"' not in line: continue
    d = json.loads(line); cid, t, msg = d.get('connId'), d.get('time',''), d.get('msg','')
    if not cid: continue
    if '建立' in msg or '连接就绪' in msg: open_t[cid] = t
    if '关闭' in msg or '断开' in msg:
        s = open_t.pop(cid, None)
        if s: pairs.append((s, t))
# 统计 <14s 的占比、均值、极值
```

**结论形式**：「23/25 条连接精确存活 12.0s；修复后 950s」——这种数字比任何描述都有说服力。

**其它高频判据**：
- WS 日志的 **`channels` 计数**：`>0` 说明卡片已挂载；`=0` 说明画布没渲染（见 [03 §3.1](./03-前端框架与布局.md)）；
- 数据源 `status`：`idle` / `online` / `reconnecting` / `error`。

## 6.4 产物 grep 的注意事项

- **scoped CSS 的属性选择器插在中间**，正则要留出这段：
  `.ma-drawer__body[data-v-xxxx]>*{flex-shrink:0}`（不是 `.ma-drawer__body>*`）；
- CSS 与 JS 的哈希**每次构建都会变**，先 `ls dist/assets/` 确认最新文件名；
- 动态 import 的代码（如 `amapLoader`）会进**对应渲染器的分块**，不在主包 `index-*.js` 里
  —— 曾据此误判"安全密钥代码没进产物"，实际在 `MapRenderer-*.js` 中。

## 6.5 死代码检测：接口声明了却没人调用

**案例**：`AMapMap` 接口声明了 `setMapStyle()`，全仓 grep 只有声明处一处命中 →
说明该能力**从未接线**，所谓"支持切换"是假的。

```bash
grep -rn 'setMapStyle' web/src      # 只有 utils/amapLoader.ts 的 interface 一处 → 死代码
```

**凡是"文档/接口说支持，但现象不支持"，第一步就 grep 方法名验证是否真的被调用过。**

## 6.6 临时实例（不影响用户正在跑的服务）

用环境变量换端口 + 独立数据副本：

```bash
MONITORALL_SERVER_HTTPADDR=:9080 \
MONITORALL_STORE_DSN=/tmp/vtest/monitorall.db \
MONITORALL_SERVER_DATADIR=/tmp/vtest \
./server/bin/monitorall --config server/config.yaml
```

MediaMTX 同理：`MTX_APIADDRESS=:19997 MTX_HLSADDRESS=:18888 ...` 可起临时实例验证配置。

## 6.7 前端静默失败的可观测性（建议保留的兜底）

1. `main.ts` 全局 `error` / `unhandledrejection` 监听 → 写进 `uiStore.error` 并显示；
2. 空状态展示 `dashboardStore.error`；
3. 关键渲染器挂诊断出口（如地图的 `window.__maMap`），让用户能在控制台直接验证：
   ```js
   __maMap.getMapStyle()                          // 当前样式
   __maMap.setMapStyle('amap://styles/dark')      // 手动切换看是否渲染
   ```
4. 画布诊断角标（临时）：显示 store 状态 + DOM 实测（容器尺寸 / 项数 / 首项尺寸），
   用于区分「store 没数据」与「渲染不可见」。

**判读口诀**：
- `卡片=N张` 但 `DOM 项数=0` → 渲染层问题（模板解析 / 组件传参）；
- `channels=0` → CardHost 未挂载；
- 两者都正常但没画面 → 数据/订阅层问题。
